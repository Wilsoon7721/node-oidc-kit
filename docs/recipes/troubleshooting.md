Every `AuthError` carries a `code`. What each one means, and what to change.

| Error / code                                                | What happened                                                                                    | Fix                                                                                                                   |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `INVALID_CONFIG`                                            | A required config value is missing, such as `redirectUri` when starting a login                  | Set it; a verify-only client needs no `redirectUri`                                                                   |
| `ISSUER_MISMATCH`                                           | Discovery, or the callback's `iss`, names a different issuer than you configured                 | Check the configured issuer, or set `expectedIssuer` when the difference is deliberate                                |
| `DISCOVERY_FAILED`                                          | `/.well-known/openid-configuration` unreachable or incomplete                                    | Check the issuer URL and network egress                                                                               |
| `TOKEN_VERIFICATION_FAILED`, message mentions the signature | Forged token, or the provider rotated keys                                                       | Retry once (the library refetches the JWKS itself); if it persists, the provider's published keys are wrong           |
| `TOKEN_VERIFICATION_FAILED`, message mentions `aud`         | ID token minted for another `client_id`, or an ID token passed to `verifyAccessToken`            | Verify ID tokens with the client they were issued to; pass the access token to API verification                      |
| `TOKEN_VERIFICATION_FAILED`, message mentions `iss`         | Token from a different provider deployment                                                       | Align the configured issuer with the provider's                                                                       |
| `TOKEN_VERIFICATION_FAILED` - "Token has expired"           | Clock skew or a genuinely old token                                                              | Check server clocks; raise `clockToleranceSeconds` only for real skew                                                 |
| `TOKEN_VERIFICATION_FAILED` - "no longer active"            | The shared session was revoked, or superseded by a newer one                                     | Send the user back through login                                                                                      |
| `STATE_MISMATCH`                                            | `state` missing or different, often because the transient cookie was lost                        | Make the cookie `SameSite=Lax` (not `Strict`) with the right `path`, and don't start several logins in parallel       |
| `NONCE_MISMATCH`                                            | The ID token was not bound to this authorization request                                         | Use the same storage for authorize and callback, and don't replay a callback URL                                      |
| `INVALID_CALLBACK`                                          | No `code`, or the PKCE verifier is gone                                                          | The login attempt expired (10 min); start again from your login route                                                 |
| `AUTHORIZATION_RESPONSE_ERROR`                              | The provider returned `?error=` (e.g. `access_denied`)                                           | Expected when a user declines consent; send them back to your login page                                              |
| `STORAGE_UNAVAILABLE`                                       | A storage-backed call with no usable storage, or a cookie write in a Server Component            | Pass a storage implementation; move cookie writes into a Route Handler, Server Action or middleware                   |
| `SILENT_AUTH_UNAVAILABLE`                                   | `silentAuthorize()` was called with no browser document                                          | Server-rendered apps keep tokens server-side and refresh them instead                                                 |
| `FOREIGN_SESSION`                                           | The session cookie holds another application's tokens, and this client cannot resolve them      | Configure a profile that resolves shared sessions, `apiAudience` and a `clientSecret`, or give this app its own cookie |
| `PROFILE_REQUIRED`                                          | A provider-specific method (escalation, `verifyPlatformSession`, ...) was called with no profile | Pass the provider's profile, e.g. `profile: wilsoon()`                                                                |
| `SESSION_CHECK_UNAVAILABLE`                                 | `isSessionCurrent()` had no way to resolve the live session version                              | Configure `resolveSessionVersion` on the profile, or pass `{ token }` with a `clientSecret` set                       |
| `INTROSPECTION_UNAVAILABLE`                                 | No `clientSecret`, or the provider advertises no introspection endpoint                          | Introspect from your server with a confidential client                                                                |
| `CLAIM_INVALID` - "audience this resource server accepts"   | A shared session but no `apiAudience` configured                                                 | Set `apiAudience`, or expect only your own ID token                                                                   |
| `CLAIM_INVALID` - "does not satisfy"                        | The token's `acr` is weaker than `requiredAcr` demanded                                          | The provider ignored or could not meet `acr_values`. This is the check working                                        |
| `CLAIM_INVALID` - "Missing required permission(s)"          | `requirePermission()` found a permission missing                                                 | Expected for a user without it; if every user fails, check `permissionsClaim` or the profile                          |
| `MACHINE_TOKEN_NOT_ALLOWED`                                 | A `client_credentials` token reached a path that expects a user                                  | Pass `allowMachineTokens: true` and branch on `tokenUse`, or use `verifyMachineToken()`                               |
| `NOT_A_MACHINE_TOKEN`                                       | A user token was passed to `verifyMachineToken()`                                                | Use `verifyAccessToken()` for user tokens                                                                             |
| `INVALID_CHALLENGE`                                         | `createStepUpRequest()` got a header it could not parse, or one naming no `acr_values`/`max_age` | Check `isStepUpChallenge()` first; an ordinary 401 is answered with a plain login                                     |
| `ACCESS_DENIED`                                             | The user refused a step-up, an escalation or a device authorization                              | Expected; tell them what was declined rather than retrying                                                            |
| `EXPIRED_TOKEN`                                             | The escalation or device code passed its deadline                                                | Start the flow again. Only the server decides this; don't add a client-side timeout                                   |
| `ESCALATION_FAILED`                                         | Unknown method (`invalid_use`), unusable `id_token_hint`, or an unknown subject                  | Check `use` against what the provider supports, and pass an `idTokenHint` you were issued                             |
| `DEVICE_FLOW_FAILED`                                        | Not registered for the grant, device code already redeemed, or no endpoint advertised            | Enable the grant on the client; device codes are single use                                                           |
| `CRYPTO_UNAVAILABLE`                                        | The runtime has no Web Crypto                                                                    | Node.js 18+, a modern browser, or an edge runtime                                                                     |
| Every user is signed out once after upgrading to 3.0        | Storage names changed from `wilsoon_*` to `oidc_*`                                               | Pass the provider's profile, which keeps the old names, or set `storagePrefix`                                        |
| `roles` / `permissions` always empty                        | No `rolesClaim` / `permissionsClaim` and no profile                                              | Tell the client where your provider puts them. See [Authorization](/recipes/authorization)                            |
